Executive Recommendation

Build this as a deterministic analysis core plus bounded Claude agents, not as a pure code-generation agent. The context graph should be the product’s source of truth. Agents should read through graph tools, write structured artifacts, and pass judge/linter/runtime gates before downstream stages can run.

1. Graph-first comprehension

Parse COBOL into AST/ASG-derived entities, data lineage, transaction boundaries, file/DB/CICS/JCL touchpoints, and runtime traces. Store this in Neo4j with source spans and evidence pointers.

2. Seam-led delivery planning

Detect external seams, data seams, batch seams, API/CICS seams, copybook/domain seams, and co-change seams. Use them to form modernization increments and story clusters.

3. Gate every generated artifact

BRDs, stories, designs, tests, and Java code must have evidence coverage, LLM-as-judge scores, compile gates, architecture rules, and COBOL-vs-Java regression harness results.

Model note: Anthropic’s current docs list Claude Opus 4.8 and Claude Sonnet 4.6 as latest models, with Opus 4.8 recommended for complex reasoning and long-horizon agentic coding. Use Opus 4.8 for planning, judging, and hard decomposition; use Sonnet 4.6 for high-throughput extraction, summarization, and code/test generation unless a gate fails.

Thoughtworks Modernization Doctrine

The platform should encode the Thoughtworks/Fowler approach as product behavior, not as background reading. The north star is not automated feature parity. It is validated understanding, business-outcome-led decomposition, and incremental displacement through well-chosen seams and transitional architecture.

Outcomes before technology

Legacy displacement begins by clarifying the business outcome: lower cost of change, better process, retirement risk, regulatory pressure, or faster product change. “Java 25 and Spring Boot 4” are implementation choices, not sufficient reasons to modernize.

Avoid feature-parity traps

The platform must flag large “copy the current system exactly” plans as risky. Feature parity often drives big-bang migration and preserves obsolete business process constraints. BRDs should distinguish required behavior from accidental legacy behavior.

Reconstruct functional intent

For each capability, combine code, data, screens, files, JCL, runtime traces, logs, and SME knowledge into a traceable functional specification. The BRD is a reviewed blueprint for forward engineering, not a prettified code summary.

Lineage is mandatory

Every generated claim must carry lineage: source span, graph node, runtime observation, or SME confirmation. This directly counters hallucination and creates the confidence needed for business review.

Incremental displacement

Modernization increments should be built around seams that let new behavior coexist with legacy behavior. Cutover patterns include dual run, fork on ingress, event interception, diverting flow, and legacy mimic adapters.

Macro first, then micro

Generate larger services around vertical business capabilities first. Split into smaller microservices only when data ownership, release independence, observability, and operating model maturity are present.

How This Changes the Product

  • The first-class artifact is a validated functional blueprint, not generated Java code.
  • The platform should include a business outcome capture step before parsing and planning.
  • The graph schema should include Outcome, Capability, Observation, Lineage, TransitionPattern, and Approval nodes.
  • The BRD judge should penalize requirements that lack lineage, preserve obsolete process constraints without justification, or skip user/SME validation.
  • The story planner should optimize for independently releasable increments, not just graph clusters.
  • The service designer should recommend a modular monolith or macroservice when microservice extraction would create distributed data coupling.

COBOL Parsing Strategy

The existing local project already wraps a ProLeap-based Java extractor and maps JSON into graph entities. Keep that path for v1 because ProLeap exposes AST and ASG concepts, handles preprocessing, and has evidence of use on banking and insurance COBOL. Add a fast file-discovery and parallel execution layer around it rather than replacing it early.

Parser optionFitRecommendation
ProLeap ANTLR4 COBOL parser Strong AST/ASG, COPY/REPLACE preprocessing, data/control-flow concepts, EXEC SQL/CICS text extraction. Primary v1 parser. Extend the existing extractor contract to emit data items, file IO, EXEC SQL, EXEC CICS, JCL linkages, and source spans.
Tree-sitter COBOL grammar Fast, robust, incremental parsing style, but COBOL grammars are less semantically rich and may need custom queries. Use as optional fast pre-scan for indexing, symbol hints, and editor features. Do not depend on it as the only semantic parser.
Koopa / other COBOL parsers Useful fallback for difficult dialects or independent parse verification. Add later as a parser adapter for parser disagreement detection and dialect coverage.
Custom Python parser High risk for COBOL dialects, copybooks, fixed/free format, CICS, SQL, and production corner cases. Avoid except for lightweight lexical scanning and JCL/control-card parsing.

Extractor Contract Extensions

  • Program, Division, Section, Paragraph, Sentence, Statement, Copybook, DataItem, FileDescriptor, SQLBlock, CICSTransaction, JobStep.
  • Relationships: CONTAINS, PERFORMS, CALLS, COPIES, READS, WRITES, DECLARES, USES_DATA, MOVES_TO, EXECUTES_SQL, EXECUTES_CICS, SCHEDULES.
  • Properties: source dialect, copybook resolution status, paragraph order, line span, cyclomatic estimate, IO mode, table/file name, transaction ID, confidence, parse errors.

Graph Principles

  • Every generated requirement, story, design decision, and test must link back to source nodes or runtime evidence.
  • Store summaries as graph node properties, but keep raw source slices in object storage or repo snapshots to avoid graph bloat.
  • Generate Cypher on the fly only through a read-only query agent that validates labels, relationship types, limits, and forbidden clauses before execution.
  • Use graph traversal before vector retrieval for code relationships; use vector retrieval for business phrasing, summaries, and cross-cutting concepts.

Prompt and Context Engineering

  • Stable system prompts, schema definitions, graph tool descriptions, and domain taxonomy should be cacheable prompt prefixes.
  • Use map/reduce for large codebases: subsystem agents produce compact structured summaries; reducer agents merge and preserve evidence maps.
  • Use subagents only when their scope is independent: one subsystem, one seam candidate, one story cluster, one service module.
  • Use prompt compression after each phase: raw graph traversals become signed summaries with source references and token budgets.
  • Record model, prompt version, graph snapshot, token usage, cache reads/creation, and judge outputs for reproducibility.

Seam Discovery Model

Seams are modernization control points: places where behavior can be isolated, replaced, tested, or routed incrementally. Use multiple graph signals rather than asking an LLM to guess.

Score Formula

Business criticality Isolation Testability Data ownership clarity Replacement risk

Rank seams by weighted score: 0.25*business + 0.20*isolation + 0.20*testability + 0.20*data_ownership - 0.15*risk. Keep the weights configurable per client and show the contributing evidence.

Thoughtworks Seam Criteria

Promote seams that are observable, externally divertable, usable without invasive legacy edits, and funnel-shaped. For mainframes, the platform should look first at external interfaces, batch file ingress, customer-facing APIs, database reader/writer boundaries, batch pipeline handoffs, downstream processing handoffs, and data-characteristic partitions.

Artifact Pipeline

BRD Generation

Use graph map/reduce. Each subsystem agent produces requirements with evidence pointers. The reducer deduplicates and renders HTML. The judge scores completeness, accuracy, clarity, consistency, and actionability. A groundedness check fails hallucinated references before human review.

Epics and Stories

Split the BRD by seam and dependency graph, not by arbitrary feature headings. Each story must include source evidence, acceptance tests, data dependencies, target service, migration toggle strategy, and rollback notes.

Service Design

Generate bounded contexts from seams, data ownership, transaction boundaries, and business capability names. Prefer modular monolith or macroservices first when boundaries are weak; promote to microservices when data ownership, independent release, and operational autonomy are clear.

Code and Tests

For each independent story cluster, run TDD: generate tests from BRD and golden-master data, generate Spring Boot code, compile, run tests, run architecture checks, then compare against COBOL behavior.

Implementation Roadmap

  1. Outcome and discovery foundation: capture modernization outcomes, system boundaries, known workarounds, source inventory, runtime evidence sources, and SME validation workflow.
  2. Graph foundation: fork/reuse the existing source graph project, preserve its FastAPI/Neo4j/Next.js/Claude Agent SDK structure, and add a product-level job/artifact model.
  3. COBOL graph depth: extend the extractor beyond programs/sections/paragraphs to data division, file IO, SQL/CICS, copybooks, JCL, runtime observations, and lineage.
  4. Blueprint v1: productionize the existing map/reduce BRD generator as a functional blueprint generator with HTML reports, evidence coverage, judge reports, prompt caching, and version history.
  5. Graph explorer: add COBOL-specific filters, seam overlays, source-slice panel, dependency paths, lineage views, and Cypher-assistant query cards.
  6. Seam engine: implement deterministic seam candidate queries and LLM explanations; attach scores, transition patterns, risk, cost, and business increment options.
  7. Increment planner: generate epics/stories/dependencies from blueprint plus seams; render HTML and graph view around independently releasable increments.
  8. Design generator: create modular monolith, macroservice, or microservice/API/domain/data designs with ADRs and verification gates.
  9. Codegen workbench: generate one approved story cluster at a time, with TDD, compile gates, repair loops, and traceability back to requirements.
  10. Equivalence lab: run COBOL and Java side by side with generated and captured test data; diff outputs, DB/file effects, and non-functional baselines.
  11. Deployment automation: generate transitional architecture components, containers, CI pipelines, smoke tests, observability, and promotion gates.

Key Risks

  • COBOL dialect variance: fixed/free format, copybook resolution, preprocessor directives, CICS, embedded SQL, vendor extensions, and JCL can break naive parsing.
  • False confidence from LLM outputs: require evidence maps, graph refs, judge reports, and human review checkpoints for business artifacts.
  • Microservice over-extraction: use seams and data ownership to decide service boundaries; default to modular monolith where boundaries are uncertain.
  • Behavioral equivalence gaps: generated tests must include captured production-like inputs, edge cases, file layouts, numeric precision, dates, and persistence side effects.
  • Cost and latency: map/reduce, prompt caching, model routing, batch jobs, and artifact reuse are mandatory for large estates.
